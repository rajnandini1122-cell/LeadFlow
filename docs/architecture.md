# Architecture

## Shape: modular monolith, two processes

Spec §3 rules out microservices for the MVP, and that is the right call: a
four-person SME CRM has no scaling problem that service boundaries would solve,
and distributed transactions across `leads`, `activities` and `follow_ups` would
be a self-inflicted wound.

One NestJS codebase runs as **two processes from the same image**:

```
apps/api/src/main.ts     -> HTTP server  (NestFactory.create)
apps/api/src/worker.ts   -> queue runner (NestFactory.createApplicationContext)
```

### Deviation from spec §26, stated openly

The spec lists `apps/worker/` as a separate workspace. It is instead a second
**entrypoint** in `apps/api`, because the worker needs the same Prisma client,
the same domain services and the same tenant-context plumbing as the API. A
separate workspace forces either duplication or an awkward shared package, and
the two inevitably drift.

This still gives the process separation §27 requires — the worker binds no port
and can be scaled independently — with none of the duplication. `apps/worker/`
remains in the tree as a thin entry so the deployment topology is unchanged.

## Layering

```
controller   thin: HTTP shape and DTO validation, nothing else
    ↓
service      business rules, transactions, events
    ↓
repository   the ONLY place Prisma is touched, always tenant-scoped
    ↓
Prisma + tenant-scoping extension
```

Enforced structurally, not by convention: an ESLint `no-restricted-imports` rule
prevents anything outside `*.repository.ts` from importing `PrismaService`.

## Module boundaries

```
common/     config, prisma, redis, tenancy, errors, audit, logging, utils
modules/
  auth  users  organizations  roles  permissions        # Phase 1 ✅
  leads                                                 # Phase 1 read-only ✅
  contacts  activities  follow-ups                      # Phase 2, 5, 6
  whatsapp  notifications  files                        # Phase 8, 10
  dashboard  reports                                    # Phase 4
  subscriptions  billing  super-admin                   # Phase 6
```

Each module owns its data. Cross-module reads go through the owning module's
service, never by importing another module's repository — this is what keeps a
future extraction into a service a mechanical change rather than an archaeology
project.

## Key decisions

### TypeScript 5.9.3, not 7.x

TypeScript 7 is the Go-based native compiler. It ships **no programmatic
compiler API**, and `nest build` calls `createProgram()`/`program.emit()` with
its own transformers. Neither it nor the Swagger CLI plugin, `ts-jest`,
`ts-loader`, or type-aware ESLint rules run on it. TS 6 is beta only.

**Revisit when:** TS 7.1 ships its new API *and* NestJS adopts it.

### Prisma 7 with a driver adapter

Prisma 7 removed the Rust query engine. Consequences we had to design around:

- a driver adapter (`@prisma/adapter-pg`) is **mandatory**;
- `url` is no longer permitted in `schema.prisma` — migration connection details
  live in `prisma.config.ts`, runtime connection in the adapter;
- the generator is `prisma-client` (not `prisma-client-js`), `output` is
  required, and it emits **TypeScript source** compiled with the project;
- ESM is the default — we set `moduleFormat = "cjs"` for NestJS decorator emit;
- `$use` middleware is **removed**, which is fine: tenant scoping uses
  `$extends`, the supported replacement.

### UUIDv7 primary keys

Random v4 keys scatter inserts across the whole index, causing page splits and
cache churn on high-write tables like `lead_activities`. v7 embeds a millisecond
timestamp in the leading 48 bits so inserts append to the right edge.

Generated by a `uuidv7()` SQL function created in migration `..._init`, and
mirrored in [uuid.ts](../apps/api/src/common/utils/uuid.ts) for
application-side ids. The migration skips its definition if one already exists,
so upgrading to Postgres 18 silently adopts the built-in.

### Authentication

- **Access token:** JWT, 15 min, claims `{ sub, org, role, sid, jti }`.
- **Refresh token:** opaque 256-bit random, 30 days. Only a SHA-256 hash is
  stored — a database disclosure yields no usable tokens. SHA-256 rather than
  argon2 is correct here: the input already carries 256 bits of entropy, so
  there is no dictionary to defend against.
- **Rotation with reuse detection:** replaying a revoked token means it leaked,
  so the entire session family is revoked. We cannot tell the victim from the
  attacker, so both re-authenticate.
- **Immediate logout:** a Redis deny list keyed by `jti`, expiring when the
  token would have anyway, so the list stays bounded.
- **Storage:** web keeps the refresh token in an `httpOnly` cookie and the
  access token in memory only — anything readable by JavaScript is readable by
  injected JavaScript. Android uses `EncryptedSharedPreferences`.

### Graceful degradation

Redis is a cache and a deny list, never the source of truth. If it is
unreachable the API falls back to Postgres and keeps serving — verified by
running the API with Redis down: login succeeded in 99 ms.

This requires `enableOfflineQueue: false` on the ioredis client. With the
default `true`, commands issued while disconnected are *queued* rather than
rejected, and every caller hangs — turning a cache outage into an API outage.

`/readiness` additionally bounds each dependency check with its own timeout: a
socket stuck mid-reconnect may never resolve or reject, and a probe that hangs
is worse than one reporting failure.

## Follow-up engine (Phase 6, designed now)

The core product promise. Schema and job contracts are fixed now because they
constrain the data model.

**Idempotency** (spec §11), by two mechanisms:

1. **Deterministic job IDs** — `followup:{id}:DUE`. BullMQ deduplicates on job
   ID, so a scheduler running twice enqueues once.
2. **Conditional transitions** — `UPDATE follow_ups SET status='DUE' WHERE id=$1
   AND status='UPCOMING'`. A second execution updates zero rows. Notifications
   carry a unique `dedupe_key`, so a duplicate send is a constraint violation
   caught and ignored, not a duplicate push.

Escalation thresholds live in `organization_settings`, never in code, so they
can become tenant-specific without a deploy.

**Timezones:** all timestamps are `timestamptz` in UTC, but "today's follow-ups"
is computed in the *organization's* zone. A server computing "today" in UTC
gives Indian users a day boundary at 05:30 local.

## WhatsApp (Phase 10, designed now)

A `WhatsAppProvider` interface with `MetaWhatsAppProvider` behind it, resolved
from `organization.whatsapp_provider`. Nothing outside
`modules/whatsapp/providers/` may import a provider SDK.

Webhooks verify the `X-Hub-Signature-256` HMAC **before** parsing, and dedupe on
`provider_message_id` (unique index), so redelivery is safe.

Meta's business verification and template approval can take weeks. The
abstraction means Phases 1–9 are unblocked by it, and the MVP `whatsapp://`
deep-link flow gives salespeople a working action from day one.
